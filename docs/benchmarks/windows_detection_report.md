## Expected False Positives in Production

- **WIN-001**: Management agents and installers that pass scripts with -EncodedCommand (for example SCCM or Intune scripts). Allow-list them by signed parent process and host group, not by command line.
- **WIN-002**: Security products (Defender MsMpEng.exe, EDR sensors) and Windows Error Reporting legitimately read LSASS memory. Exclude them by verified executable path and signature.
- **WIN-003**: Rare. Troubleshooting sessions may dump processes with comsvcs.dll, but dumping lsass.exe this way should always be investigated.
- **WIN-004**: Software deployment tools and legitimate PsExec use by administrators install short-lived services that run cmd. Correlate with change records.
- **WIN-005**: Administrative and vendor maintenance tasks often run PowerShell. Baseline existing task names per host group and alert on new ones.
- **WIN-006**: Legacy logon or inventory scripts in VBScript that call PowerShell. Allow-list them by script path.
- **WIN-007**: A misconfigured service or a stale mapped drive retrying old credentials across several accounts, and NAT or proxy addresses aggregating many users. Check whether the accounts exist and whether any attempt later succeeded.
- **WIN-008**: Legacy service accounts whose msDS-SupportedEncryptionTypes still allows only RC4, and old clients that cannot do AES. Inventory those SPNs and move them to AES rather than allow-listing the requester.
- **WIN-009**: A legacy application server that opens sessions to many RC4-only services at startup. It repeats on a schedule from a fixed host; an interactive burst from a workstation does not.
- **WIN-010**: A service or scheduled task with a changed password retrying every minute, a user locked out on a mobile device, and shared terminal servers or NAT addresses. Check SubStatus (0xc000006a wrong password, 0xc0000064 unknown user) and whether a success followed.
- **WIN-011**: Applications that validate stored credentials for many accounts, and workstation names that are blank or spoofed, since 4776 records the name the client supplies. Pair with 4625 on the target and network logs before blocking a host.

## Limits

- Ground truth is per capture. OTRF gives one technique per capture, and each capture also contains normal background activity. Precision here is analyst-reviewed hits in these captures, not a false-positive rate on a production estate.
- The OTRF captures come from one lab configuration (Sysmon and audit policy) recorded in 2020. Rules depending on 4688 command lines or Sysmon 10 need the same logging.
- `empire_psexec_dcerpc_tcp_svcctl` is mapped by OTRF to T1021 Remote Services. WIN-004 detects the service-execution part (T1543.003, T1569.002), not the remote logon itself.
- Each credential-access capture holds one short attack from one source, with almost no benign authentication around it. The captures prove the rule logic and its field names on real Windows output, not the thresholds on domain-controller volume.
- `splunk_t1558_003_unusual_kerberos_service_tickets` was altered after capture. It requests RC4 tickets for service names such as `kr1btgt` and `krbtg2t` that the KDC grants with status 0x0, which a real KDC refuses for unknown SPNs. Its 159 lines hold 90 distinct events but only 44 distinct EventRecordIDs, so one record appears with several service names, and the 43-request burst shares one timestamp. Every record carries TicketOptions 0x60810010, as the unaltered krbtgt requests do. Identical lines are indexed once. The capture tests the count logic of WIN-008 and WIN-009, not realistic Kerberoasting of service accounts; its isolated hits outside the burst are dispositioned FP.
- The EVTX-to-MITRE-Attack NTLM capture is named after 4776 and 4625 but holds only 4625 events, so WIN-011 is measured on the two splunk/attack_data captures alone.
- `--deploy` gives the native rules a 2,500-day lookback so they reach the old captures. EQL rules deduplicate on the source event, but an aggregating ES|QL row has no source event, so WIN-007 and WIN-009 to WIN-011 raise the same alert again on every five-minute run. In production, set the lookback close to the run interval.
